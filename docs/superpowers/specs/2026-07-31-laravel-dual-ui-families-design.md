# Laravel 前后台双 UI 家族设计

## 1. 文档目的

本文档定义 `co_crmv5` 在 Laravel 8、Blade 前后端不分离架构下，同时维护两套 UI 家族的设计与工程边界。

本设计不是前后端分离方案，也不是框架迁移方案。它要求在保留现有路由、控制器、API、认证和 Blade 渲染模式的前提下，将以下四个落点建设为高质量、可长期维护的正式界面：

1. 前台 A：Layui + Blade
2. 后台 A：Layui + Blade
3. 前台 B：CRMUI + Blade
4. 后台 B：CRMUI + Blade

`/front-naive` 与 `/admin-naive` 暂时保留为跳转层，不视为独立 UI，也不纳入本轮视觉实现。

## 2. 已确认目标

- A 和 B 是两套明确不同的视觉家族，不做成同一套皮肤。
- 两套家族都必须达到生产级质量，不把其中任意一套定义为临时迁移来源。
- 同一业务能力在前台 A/B 或后台 A/B 中保持功能一致，允许视觉层级和交互呈现不同。
- 继续使用 Laravel Blade，不引入 Vue SPA、React SPA 或新的前后端分离工程。
- 复用现有业务接口、权限、认证、国际化和数据结构，不因 UI 升级改写业务语义。

## 3. 当前 UI 边界

### 3.1 家族 A：Layui

- 前台视图命名空间：`front_layui::`
- 后台视图命名空间：`admin_layui::`
- 前台模板：`resources/front/layui/`
- 后台模板：`resources/admin/layui/`
- 前台主要资源：`public/css/front/`、`public/js/apps/front/layui/`
- 后台主要资源：`public/css/admin/`、`public/js/apps/admin/layui/`

家族 A 的设计方向是稳定、克制、紧凑、功能导向。它强调可扫描性、熟悉感和高频任务效率，不保留 Layui 默认样式中粗糙或过时的视觉质感。

### 3.2 家族 B：CRMUI

- 前台视图命名空间：`front_crmui::`
- 后台视图命名空间：`admin_crmui::`
- 前台模板：`resources/front/crmui/`
- 后台模板：`resources/admin/crmui/`
- 共享视觉资源：`public/css/crmui/`
- 前台脚本：`public/js/apps/crmui/front.js`
- 后台脚本：`public/js/apps/crmui/admin.js`

家族 B 的设计方向是现代、精致、层级明确、品牌感更强。它允许更成熟的设计 Token、空白节奏、状态表达和微交互，但仍然保持 CRM 工具的工作效率。

### 3.3 不计入正式 UI 的入口

- `/front-naive`
- `/admin-naive`
- `resources/views/ui-samples/`

前两者继续作为兼容跳转入口；`ui-samples` 仅作为预览和验证空间，不承担生产业务页面职责。

## 4. 设计系统架构

采用“共享 UX 基线 + 两个 UI 家族 + 前后台页面覆盖”的三层结构。

### 4.1 共享 UX 基线

共享层只定义与视觉家族无关的产品规则：

- 可访问性：对比度、键盘导航、焦点状态、语义标签。
- 响应式：移动端、平板、桌面和宽屏断点行为。
- 状态：加载、空数据、成功、失败、禁用、权限不足和网络异常。
- 表单：可见标签、字段分组、就近校验、提交中状态和错误恢复。
- 表格：筛选、分页、批量操作、固定列、空状态和窄屏降级。
- 反馈：按钮状态、操作结果、危险操作确认和长任务进度。
- 国际化：中英文长文本、数字、日期、金额和时区呈现。

现有 `design-system/co-crm/MASTER.md` 作为共享设计基线的起点，实施前需要结合本文档复核，不直接把其中某一种具体风格强制应用到 A/B 两个家族。

### 4.2 家族 A 规则

- 低到中等视觉变化度。
- 后台高密度，前台中等密度。
- 使用清晰边框、稳定间距和有限层级。
- 卡片只用于真正独立的内容单元，不堆叠卡片。
- 表格、筛选器和批量操作优先保障扫描与操作速度。
- 动效保持短促克制，仅用于状态变化和空间关系。

### 4.3 家族 B 规则

- 中等视觉变化度，允许更强的层级和品牌识别。
- 后台中高密度，前台中低密度。
- 使用系统化 Token 管理颜色、圆角、阴影、间距和交互状态。
- 强化空状态、加载骨架、页面标题区和关键任务引导。
- 使用更精细的表格工具栏、状态标签、侧栏和详情结构。
- 动效用于反馈、展开、切换和加载，不做纯装饰动画。

### 4.4 前台与后台覆盖

同一家族内，前后台保持同一视觉语言，但职责不同：

- 前台强调任务理解、信息解释、资金操作安全和移动端可用性。
- 后台强调数据密度、批量处理、筛选效率、权限可见性和审计能力。

前后台差异通过布局密度、导航结构、页面覆盖规则和组件配置实现，不另建第三种视觉语言。

## 5. 页面与资源隔离原则

- 每个 Blade 页面只属于一个 UI 家族。
- Layui 页面不得直接引用 CRMUI 页面级样式或组件类名。
- CRMUI 页面不得依赖 Layui 的视觉选择器作为布局基础。
- `public/js/shared/` 只承载与 UI 家族无关的请求、认证、国际化和通用运行逻辑。
- 家族专属 DOM 查询、事件绑定和组件状态放在各自脚本目录。
- 可以共享业务数据和后端接口，不共享会造成视觉耦合的页面级 CSS。
- 公共 Blade partial 只复用语义稳定、无家族样式依赖的内容。

## 6. 数据流与交互边界

四个 UI 落点继续使用现有后端数据流：

1. Laravel 路由与控制器提供页面和业务入口。
2. Blade 输出页面骨架、路由信息、翻译文本和初始数据。
3. 家族专属 JavaScript 调用现有前台或后台 API。
4. API 返回的数据模型在 A/B 中保持一致。
5. 每个 UI 家族负责将同一业务状态呈现为自己的视觉与交互语言。

UI 升级不得通过复制或改写业务规则制造新的数据来源。相同业务状态必须由同一后端字段和接口决定。

## 7. ui-ux-pro-max 的职责

`ui-ux-pro-max` 是设计决策与质量审查工具，不是 UI 框架，也不会单独自动修改项目。

实施时由 Codex 或开发者调用它完成：

- 生成和校准共享 UX 基线。
- 为 Layui 家族生成稳定、紧凑、企业化的设计建议。
- 为 CRMUI 家族生成现代、精致、品牌化的设计建议。
- 为 dashboard、列表、详情、表单、认证和资金操作等页面生成覆盖规则。
- 查询 Laravel 栈、表格、表单、可访问性、图表和响应式规范。
- 在交付前执行 UI/UX 反模式与可访问性审查。

技能输出必须经过本文档的边界约束后再实施，不能因为搜索结果推荐了新框架就改变 Laravel Blade 架构。

## 8. 谁使用本文档

### 8.1 Codex

Codex 是首选实施者。每次实施前必须读取：

1. 本设计文档。
2. `design-system/co-crm/MASTER.md`。
3. 当前 UI 家族的规则。
4. 当前页面的覆盖规则。
5. 当前页面真实的 Blade、CSS、JavaScript、路由和控制器。

Codex 随后按照实施计划修改现有项目文件，并执行测试和浏览器验证。

### 8.2 人工开发者

人工开发者使用本文档判断页面属于哪个 UI 家族、哪些资源可以共享、哪些样式禁止跨家族引用，以及页面验收需要满足哪些状态。

### 8.3 后续 Codex 任务或其他代理

后续任务必须在提示中明确引用本文档，不允许仅凭截图或单页上下文重新定义整站风格。

推荐任务提示：

```text
请先读取 docs/superpowers/specs/2026-07-31-laravel-dual-ui-families-design.md，
再读取当前设计系统和目标页面文件。
在现有 Laravel Blade 项目中实现 [UI 家族] 的 [前台/后台] [页面名称]，
保持现有业务接口、权限、认证、国际化和路由行为不变。
```

## 9. 实施方式

设计文档批准后，不直接全站改造。先生成实施计划，再分批执行：

1. 建立共享 UX 基线和 A/B 家族规则。
2. 选择一个前台高频页面和一个后台高频页面作为样板。
3. 分别完成 A/B 两套样板，验证视觉差异与功能一致性。
4. 固化布局、表格、筛选器、表单、状态和反馈组件规范。
5. 按业务模块扩展到其余页面。
6. 每批完成后运行功能测试、Blade 渲染测试、浏览器桌面/移动端验证和可访问性检查。

推荐优先选择登录、dashboard、用户列表、详情或资金操作页面作为样板，因为这些页面能覆盖认证、导航、数据展示、表单和状态反馈。

## 10. 错误处理与失败原则

- 页面加载失败必须显示明确错误，不显示假数据或空白成功态。
- 表单错误必须靠近对应字段，并保留用户已输入的数据。
- API 失败不得通过静默回退掩盖。
- 权限不足与数据为空必须使用不同状态。
- A/B 两套 UI 必须对同一后端错误产生一致的业务含义。
- 实施中发现路由、接口或数据契约不一致时，先修复根因，不在每套 UI 里分别打补丁。

## 11. 验证与验收

每个实施批次至少验证：

1. 目标路由返回正确的 UI 家族页面。
2. Blade 模板可以编译和渲染。
3. 现有认证、权限、API、表单提交和跳转行为不回归。
4. 中英文界面不溢出、不重叠。
5. 加载、空数据、失败、成功、禁用和权限不足状态完整。
6. 桌面、平板和移动端页面没有无意义横向滚动。
7. 键盘焦点、对比度、图标标签和触控尺寸满足可访问性基线。
8. A 和 B 在视觉上明显不同，但同一业务功能保持一致。
9. 页面没有混用另一 UI 家族的页面级 CSS 或组件行为。

## 12. 非目标

- 不把系统改造成 SPA。
- 不新增第三套真实 UI。
- 不删除 `/front-naive` 或 `/admin-naive`。
- 不在本设计阶段重写后端业务逻辑。
- 不一次性重做所有页面。
- 不为了视觉统一强制 A/B 使用相同组件库。

## 13. 后续流程

1. 用户审核并批准本文档。
2. Codex 读取本文档并编写详细实施计划。
3. 用户审核实施计划与批次顺序。
4. Codex 在当前 `co_crmv5` 仓库内执行修改。
5. 每批修改完成后运行测试与浏览器验证。
6. 验证通过后再进入下一批页面。
