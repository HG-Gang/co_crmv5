# 一、用户注册登录模块

## 路由: GET /

- **旧项目路由名**: 无（匿名闭包）
- **对应新项目路由**: 待映射
- **调用控制器方法**: 匿名闭包（`redirect()->route('login', ['langId' => ...])`)
- **中间件**: 无
- **为什么这样做（业务目的）**: 网站根路径访问时，自动跳转到登录页面。这是入口路由，所有未登录用户访问网站首页时会自动被引导到登录界面。`langId`参数用于控制前端多语言显示（1=简体中文、2=繁体中文、3=英文）。
- **入参**:
  - langId: int, 可选（默认值1）, 语言标识
- **执行步骤（详细链路）**:
  1. Laravel路由匹配到`/`
  2. 闭包执行，从request中读取`langId`参数，默认值为`'1'`
  3. 调用Laravel的`redirect()->route('login', ...)`，通过命名路由`login`生成`/user/login?langId=1`的URL
  4. 发起302重定向响应
  5. 浏览器跳转到`/user/login?langId=1`
- **返回值**: HTTP 302 重定向
- **各执行结果中文含义**:
  - 成功: 302 → 重定向到登录页

## 路由: GET user/login

- **旧项目路由名**: login
- **对应新项目路由**: 用户登录页
- **调用控制器方法**: User\LoginController@loginGmtk
- **中间件**: 无
- **为什么这样做（业务目的）**: 展示用户登录页面。该方法是GMTK版本的登录页面渲染入口，会返回包含登录表单、验证码的HTML页面。支持多语言，根据`langId`参数加载对应语言包。
- **入参**:
  - langId: int, 可选, 语言标识（1=简体中文, 2=繁体中文, 3=英文）
- **执行步骤（详细链路）**:
  1. 路由匹配`user/login`
  2. 进入`LoginController@loginGmtk`方法
  3. 读取`langId`参数，设置`session('langId', $langId)`
  4. 根据langId加载对应的语言文件（resources/lang下的语言包）
  5. 检查session中是否有已登录用户信息，若已登录则直接跳转到用户首页
  6. 返回`user.login.login_gmtk`视图模板
  7. 视图中包含登录表单（用户名、密码、验证码）
- **返回值**: HTML页面（登录表单视图）
- **各执行结果中文含义**:
  - 成功: 200 → 展示登录页面

## 路由: POST user/signIn

- **旧项目路由名**: user.loginUrl
- **对应新项目路由**: 用户登录接口
- **调用控制器方法**: User\LoginController@signIn
- **中间件**: LoginMiddleware
- **为什么这样做（业务目的）**: 处理用户登录表单提交。验证用户名、密码和验证码，验证通过后创建session，记录登录日志（IP、时间、设备信息），更新最后登录时间。支持同时校验手机号或邮箱作为登录账号。
- **入参**:
  - userName: string, 必填, 用户名/手机号/邮箱
  - passWord: string, 必填, 登录密码（前端MD5加密）
  - captcha: string, 必填, 图形验证码
  - langId: int, 可选, 语言标识
- **执行步骤（详细链路）**:
  1. LoginMiddleware中间件执行（此时仅检查是否重复请求，不做登录态校验）
  2. 进入`LoginController@signIn`方法
  3. 校验验证码captcha是否正确（与session中存储的验证码比对）
  4. 根据`userName`在`user`表中查询用户（支持用户名、手机号、邮箱三种匹配方式）：`SELECT * FROM user WHERE user_name = ? OR user_phone = ? OR user_email = ?`
  5. 检查用户状态是否被禁用（`user_status = 0`表示禁用）
  6. 校验密码：将前端传来的MD5密码与数据库中`user_pass`字段做二次加密比对
  7. 登录成功，将用户信息写入session：`session(['user' => $userInfo])`
  8. 记录登录日志到`user_login_log`表：`INSERT INTO user_login_log (user_id, login_ip, login_time, login_device, ...)`
  9. 更新用户最后登录IP和时间：`UPDATE user SET last_login_ip = ?, last_login_time = ? WHERE user_id = ?`
- **返回值**: JSON
  ```json
  {
    "code": 1,
    "msg": "登录成功",
    "data": {
      "user_id": "xxx",
      "user_name": "xxx",
      "user_phone": "xxx"
    }
  }
  ```
- **各执行结果中文含义**:
  - 成功: code=1 → 登录成功
  - 失败: code=0 → 验证码错误 → 图形验证码输入不正确或已过期
  - 失败: code=-1 → 用户不存在 → 输入的用户名/手机号/邮箱在系统中未注册
  - 失败: code=-2 → 密码错误 → 输入的密码与注册密码不匹配
  - 失败: code=-3 → 账号被禁用 → 该用户已被管理员停用

## 路由: POST user/register/registerVerifyInfo

- **旧项目路由名**: 无
- **对应新项目路由**: 注册信息校验
- **调用控制器方法**: User\RegisterController@registerVerifyInfo
- **中间件**: 无
- **为什么这样做（业务目的）**: 在用户提交注册之前，前端实时校验注册信息是否合法。验证用户名、手机号、邮箱是否已被注册，邀请码是否有效等。
- **入参**:
  - field: string, 必填, 校验字段名（user_name / user_phone / user_email / invite_code）
  - value: string, 必填, 校验值
  - langId: int, 可选, 语言标识
- **执行步骤（详细链路）**:
  1. 进入`RegisterController@registerVerifyInfo`方法
  2. 根据`field`参数决定校验逻辑
  3. 如果field=user_name：`SELECT COUNT(*) FROM user WHERE user_name = ?`检查是否已存在

# 四、支付回调模块

## 路由: ANY user/deposit_notfiy

- **旧项目路由名**: user_deposit_notfiy
- **对应新项目路由**: 支付通道1异步回调（通用）
- **调用控制器方法**: PayController\PayCallBackController@deposit_notify_response_success
- **中间件**: LoginMiddleware
- **为什么这样做（业务目的）**: 接收第三方支付平台（通道1）的异步回调通知。支付平台在用户完成支付后，通过此URL通知服务端支付结果。这是支付系统的核心回调接口。
- **入参**（由支付平台POST）:
  - order_no: string, 必填, 商户订单号
  - trade_no: string, 必填, 支付平台交易号
  - amount: decimal, 必填, 实际支付金额
  - status: int, 必填, 支付状态
  - sign: string, 必填, 数字签名（用于验证请求真实性）
- **执行步骤（详细链路）**:
  1. 接收回调POST数据
  2. 验证数字签名：根据支付通道的签名规则，用商户密钥重新计算签名并与sign参数比对
  3. 签名验证失败则拒绝处理，返回"FAIL"
  4. 根据order_no查询订单：`SELECT * FROM deposit_order WHERE order_no = ?`
  5. 检查订单状态是否为"待支付"（status=0），如果不是则跳过（防止重复回调）
  6. 校验回调金额与订单金额是否一致
  7. 更新订单状态：`UPDATE deposit_order SET trade_no = ?, paid_amount = ?, status = 1, pay_time = NOW() WHERE order_no = ?`
  8. 增加用户账户余额：`UPDATE user_account SET balance = balance + ? WHERE user_id = ?`
  9. 插入资金流水记录：`INSERT INTO fund_flow (user_id, order_no, type, amount, balance_before, balance_after, create_time) VALUES (?, ?, 'deposit', ?, ?, ?, NOW())`
  10. 计算返佣：查询用户上级代理关系链，按佣金比例计算并分配佣金
  11. 返佣入账：`UPDATE user_account SET balance = balance + ? WHERE user_id = ?`（各级代理）
  12. 返回"SUCCESS"给支付平台
- **返回值**: 纯文本"SUCCESS"或"FAIL"
- **各执行结果中文含义**:
  - 成功: 返回"SUCCESS" → 支付确认完成，余额已增加
  - 失败: 返回"FAIL" → 签名验证失败或订单不存在
  - 重复回调: 返回"SUCCESS" → 订单已处理（幂等性保证）

## 路由: POST user/withdraw_request

- **旧项目路由名**: 无
- **对应新项目路由**: 在线提现请求
- **调用控制器方法**: User\UserWithdrawController@withdraw_request
- **中间件**: LoginMiddleware
- **为什么这样做（业务目的）**: 用户提交在线提现申请。验证身份后创建提现订单，等待后台审核或自动处理。
- **入参**:
  - amount: decimal, 必填, 提现金额
  - bank_id: int, 必填, 选择的银行卡ID
  - password: string, 必填, 资金密码/登录密码
  - verify_code: string, 可选, 验证码（取决于系统配置）
- **执行步骤（详细链路）**:
  1. 校验提现金额是否在允许范围内（最低、最高限制）
  2. 校验账户余额是否充足
  3. 校验资金密码是否正确
  4. 检查是否有未处理的提现订单
  5. 生成提现订单号
  6. 预扣账户余额或冻结金额：`UPDATE user_account SET balance = balance - ?, frozen_amount = frozen_amount + ? WHERE user_id = ?`
  7. 插入提现订单：`INSERT INTO withdraw_order (order_no, user_id, amount, bank_id, status, create_time) VALUES (?, ?, ?, ?, 0, NOW())`
  8. 返回提交结果
- **返回值**: JSON
  ```json
  {"code": 1, "msg": "提现申请已提交，等待处理"}
  ```
- **各执行结果中文含义**:
  - 成功: code=1 → 提现申请提交成功
  - 失败: code=0 → 余额不足
  - 失败: code=-1 → 金额不在允许范围
  - 失败: code=-2 → 密码错误
  - 失败: code=-3 → 有未完成的提现订单，请等待处理完毕

- **为什么这样做（业务目的）**: 后台管理员审核出金申请，通过或拒绝，并处理资金变动。
- **入参**:
  - order_id: string, 必填, 订单号
  - action: string, 必填, 操作（pass=通过, nopass=拒绝）
  - remark: string, 可选, 审核备注
- **执行步骤（详细链路）**:
  1. 查询出金订单：`SELECT * FROM withdraw_order WHERE order_no = ?`
  2. 检查订单状态是否可操作
  3. 如果通过：更新订单status=1，扣减冻结金额，记录出金流水
  4. 如果拒绝：更新订单status=-1，解冻金额退回账户余额，记录退回流水
  5. 发送通知告知用户审核结果
  6. 返回结果
- **返回值**: JSON `{"code": 1, "msg": "操作成功"}`
- **各执行结果中文含义**:
  - 成功: code=1 → 出金订单处理完成
  - 失败: code=0 → 订单状态不可操作（已处理）

# 十八、附录：中间件说明

| 中间件名称 | 用途 | 应用范围 |
|---|---|---|

| permissions | 后台RBAC权限校验：检查session中的管理员信息、角色和权限列表 | 全部 `admin/` 下的路由（登录页除外） |
