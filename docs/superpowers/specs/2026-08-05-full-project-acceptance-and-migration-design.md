## 1. 目标

本轮工作必须同时解决以下问题：

1. 对全部一方维护源码建立明确清单，检查并修复可复现的业务逻辑、测试隔离和注释问题。
2. 所有自动化测试最终必须为零 Failure、零 Error；已知 flake、单独重跑通过或历史报告不能代替全量通过。
3. 使用全部最新 migration 在空库重放得到唯一权威表结构，不再从被历史操作污染的开发库反向认定“最新结构”。
4. 生成一个可独立执行的 SQL 文件，并提供执行同一文件的 Laravel Artisan 命令。
5. 将旧库 `hank_zl_data` 的全部纳入迁移范围的数据装载到目标库 `co_crmv5`。
6. 保持 `MT4_ENABLED=false` 和 `MT4_USER_SYNC_ENABLED=false`，迁移和测试期间不得建立真实 MT4 连接或分发用户同步任务。
7. 前台用户、后台管理员和大代理的初始密码统一为 `abc123`。
8. 在包含真实迁移数据的隔离数据库运行全量测试；最终目标库完成重建后再执行不破坏交付数据的登录、查询和一致性验收。

“百分百正确”不能由有限测试从数学上证明。本设计把它落实为可审计的工程门禁：纳入范围的文件和路由必须有清单；所有定义的静态检查、自动化测试、迁移校验和真实数据验收必须全部通过；不得存在被忽略的已知失败、未解释差异或假成功分支。

## 3. 当前基线与根因

当前证据不能支持旧报告中的“已经全量完成”结论：

- 最近完整 Feature 报告为 3140 个测试、30 个 Failure、2 个 Error。
- 全量测试默认继承 `.env` 并指向 `co_crmv5`，341 个 Feature 文件直接访问数据库，部分测试执行 DDL，存在污染真实库的风险。
- 注册测试未完整清理 `user_mt4_provisioning_outbox`，唯一键残留会级联导致登录和前台业务测试失败。
- 新闻翻译测试在 `DatabaseTransactions` 生命周期中执行 MySQL DDL，DDL 隐式提交后 teardown 回滚会产生 `There is no active transaction`。

- 现有 schema 快照包含 6 张历史备份表和缺少仓库 migration 的表，不能作为 migration 权威结果。
- SQL 的 DDL 使用默认库，数据语句硬编码 `co_crmv5`，预检连接与实际 SQL 数据源可能不是同一个库。
- 迁移命令只输出目标表数量，不执行源目标数量、重复键、孤儿、金额和状态校验，失败时可能返回假成功。

- 注释标准原本是第三方 HMAC 专项标准，历史处理机械扩展为文件/方法数量统计，没有证明参数来源、失败关闭和信任边界语义正确。

## 4. 总体架构

工作按以下依赖顺序推进，每一阶段的验收结果都是下一阶段的输入：

1. **版本与安全基线**：恢复远端历史用于差异查看，但不自动 add、commit 或 push；所有 Git 写操作由人工审核决定。
2. **测试隔离层**：建立只能指向专用测试库的运行入口，测试进程拒绝连接 `co_crmv5` 和 `hank_zl_data`。
3. **逻辑闭环层**：按失败域执行 TDD，先写或确认能复现问题的失败测试，再修复根因。
4. **注释语义层**：建立一方源码清单和机器门禁，对高风险代码进行人工语义复核。
5. **权威 schema 层**：在空库重放全部 migration，导出并比对结构指纹。
6. **单 SQL 迁移层**：由权威 schema、明确的数据映射和尾部安全策略生成唯一 SQL。
7. **Laravel 编排层**：命令执行预检、备份、SQL、强校验和失败报告，不复制另一套迁移逻辑。
8. **真实数据验收层**：先在隔离迁移库演练，再在真实数据克隆库跑全量测试，最后重建 `co_crmv5` 并执行非破坏性验收。

## 5. 数据库拓扑与数据流

### 5.1 固定数据库身份

- 旧数据源：`127.0.0.1:3307/hank_zl_data`，迁移期间只读。
- 最终目标：`127.0.0.1:3307/co_crmv5`。
- schema 验证库：`co_crmv5_schema_verify`，可丢弃，只用于 migration 空库重放。
- 迁移演练库：`co_crmv5_migration_verify`，可丢弃，用于执行生成 SQL 和迁移校验。
- 全量测试库：`co_crmv5_test`，可丢弃，从迁移演练库或最终目标库精确克隆真实数据后运行测试。

命令必须验证源库和目标库名称不同、主机端口与 SQL 契约一致、数据库版本满足 MySQL 8 语法要求。任何身份不一致都在写入前失败。

### 5.2 执行顺序

1. 对 `co_crmv5_schema_verify` 执行 `migrate:fresh`，不依赖当前开发库结构。
2. 从 schema 验证库导出不含数据、不含 AUTO_INCREMENT 当前值的结构。
3. 将结构、旧库数据映射、migration 记录、MT4 归零和密码策略组装成单一 SQL。
4. 在 `co_crmv5_migration_verify` 执行完整 SQL，运行全部迁移数据校验。
5. 将演练结果克隆到 `co_crmv5_test`，运行全部 Unit、Feature、逐文件隔离和业务写路径测试。
6. 修复发现的问题后，从第一步重新生成和演练，不对旧 SQL 打临时补丁。
7. 验收库全部通过后，先备份 `co_crmv5`，再由 Laravel 命令执行同一 SQL。
8. 从最终 `co_crmv5` 再克隆一次 `co_crmv5_test`，证明全量测试使用的是最终真实迁移数据。
9. 最终库只执行登录、查询、权限、统计和明确可回滚的最小冒烟，确保交付数据不被测试夹具污染。

## 6. 权威表结构与单 SQL

### 6.1 schema 唯一来源

- 权威结构只来自仓库全部 migration 在空库的成功重放。
- migration 文件集合必须与生成 SQL 写入的 `migrations` 记录一一对应。
- 不迁移 `user_*_backup_*` 等历史修复快照表。
- `personal_access_tokens` 等表只有在仓库存在对应 migration 时才能进入最终结构；否则补齐 migration 或从结构中移除。
- schema 指纹至少包含表名、列顺序与类型、NULL/default、索引、唯一约束、外键、引擎、字符集和表/列注释。

### 6.2 SQL 文件要求

最终只交付一个用户可执行文件：`database/sql/full_reset_and_migrate.sql`。

该文件必须满足：

- 明确 `USE co_crmv5`，不得在未选库状态执行 DDL。
- 执行前检查 MySQL 版本和旧库关键表/列存在性。
- 禁用外键检查前保存会话状态，结束时恢复状态。
- DROP 并重建目标库范围内全部正式表，不使用保留旧表的 `CREATE TABLE IF NOT EXISTS` 策略。
- 所有表建表时 AUTO_INCREMENT 从 1 开始；导入数据后非空表的下一值自然等于 `MAX(id)+1`，空表仍为 1。
- 从 `hank_zl_data` 迁移的每张表必须出现在迁移清单中；不迁移的旧表必须有可审计理由。
- 对 `agents` 与 `user` 的 `user_id` 冲突、邮箱冲突和唯一键冲突在写入前失败，不做静默覆盖。
- 不关闭严格 SQL 模式来掩盖截断、非法日期或类型错误；需要转换的数据必须显式转换并可测试。
- `user_infos.is_mt4_synced` 全量为 0，用户 MT4 开户 outbox 不产生可被调度器分发的 pending 行。
- `user_logins`、`admins`、`big_agents` 的密码字段统一写入经过验证的 `abc123` bcrypt hash。
- SQL 可重复从干净目标状态执行；中途失败不得输出成功标记。

## 7. Laravel 命令设计

保留一个主命令 `php artisan db:full-reset-and-migrate`，它只负责编排同一 SQL 文件，不再维护第二套 PHP 数据迁移实现。

### 7.1 预检

- 只允许 `local` 或 `testing` 环境自动执行；其他环境默认拒绝。
- 校验 SQL 文件存在、大小和 SHA-256 与构建清单一致。
- 校验当前默认连接就是 `co_crmv5`，旧连接就是 `hank_zl_data`。
- 校验 MySQL 版本、字符集、权限、磁盘空间和 `mysqldump` 可用。
- 获取 MySQL advisory lock，防止两个迁移命令并发执行。
- 检查 MT4 两个开关均为 false；任一开启立即失败。
- 检查队列 worker、scheduler 或本项目相关迁移任务不会在窗口内写库。
- 执行源表/列、主键冲突、重复邮箱和关键数据可转换性预检。

### 7.2 备份与执行

- `--dry-run` 只执行全部预检和映射统计，不写目标库。
- 正式执行前必须生成完整 `co_crmv5` dump，保存时间、大小和 SHA-256；空文件或 dump 失败立即停止。
- 非交互执行必须显式传入 `--yes`，交互执行要求人工确认准确的源库和目标库名称。
- 使用 PDO 执行单一 SQL 文件，所有异常保留原始异常链并返回非零退出码。
- DDL 无法整体事务回滚；失败时明确标记目标库不可交付，并输出已验证备份路径。不得吞错或伪造成功。

### 7.3 强制验收

命令成功必须同时满足：

- schema 指纹与 migration 权威库完全一致。
- 每个映射表的源行数、目标行数、有效/软删状态分布符合映射规则。
- 无重复业务主键、重复邮箱和违反唯一约束的数据。
- 用户、代理、权限、订单、入金、出金、交易、返佣之间无不允许的孤儿关系。
- 关键资金字段的源目标数量和 Decimal 汇总符合转换规则。
- migration 记录集合与仓库文件集合一致。
- 三类账号的密码字段全部等于统一 hash，并对该 hash 执行 `Hash::check('abc123')`。
- `MT4_ENABLED=false`、`MT4_USER_SYNC_ENABLED=false`、`is_mt4_synced=1` 数量为 0、用户开户 pending outbox 数量为 0。

任何一项失败，命令退出码必须非零，并输出具体表、规则、期望值和实际值。

## 8. 测试与逻辑闭环

### 8.1 隔离门禁

- `phpunit.xml` 或专用测试引导必须显式使用 `co_crmv5_test`，不得继承 `.env` 的 `co_crmv5`。
- 测试启动时校验数据库名匹配严格 allowlist；目标不是专用测试库时直接退出。
- 测试库在每轮全量测试前从已验证的迁移结果重建，不能依赖上轮清理脚本修补残留。
- 涉及 DDL 的测试不得与 `DatabaseTransactions` 混用；改为独立数据库快照、明确重建或不使用事务 trait。
- 测试夹具必须拥有自己创建的全部行，teardown 对 outbox、关联表和 AUTO_INCREMENT 状态进行完整恢复。

### 8.2 TDD 修复顺序

优先按根因域修复：

1. 测试库身份和生命周期。
2. 注册用户及 MT4 开户 outbox 残留。
3. 新闻翻译 DDL/事务冲突。
4. 入金幂等测试的表指纹恢复。
5. 由前三项触发的登录、个人资料和前台业务级联失败。
6. 剩余独立失败域。

每个缺陷必须先有能够稳定复现的失败测试，确认失败原因正确后再写最小修复，并执行目标测试和相关回归。不得通过放宽断言、增加任意 sleep、吞异常或把失败列入忽略清单来变绿。

### 8.3 最终测试门禁

- 全部 PHP 源文件 `php -l` 零错误。
- Composer 配置校验通过。
- Unit 套件零 Failure、零 Error。
- Feature 套件在真实迁移数据测试库中单进程零 Failure、零 Error。
- 全部测试文件逐文件隔离执行零 Failure、零 Crash；测试运行器自身必须在任一失败时返回非零退出码。
- 完整 PHPUnit 套件零 Failure、零 Error，并禁用旧结果缓存。
- 800 条路由能够完整加载，路由清单、权限映射和旧新路由闭环审计通过。
- 登录、注册、权限/数据范围、入金、出金、返佣、MT4 本地 gate、新闻、礼品和旧版兼容关键流程均有运行时证据。

单独重跑通过不能抵消全量失败；任何 flake 都是待修复问题。

## 9. MT4 边界

- 运行时和测试迁移窗口均保持 `MT4_ENABLED=false`、`MT4_USER_SYNC_ENABLED=false`。
- `config/mt4.php` 的安全默认值必须为 false，`.env.example` 必须明确声明两个开关。
- 所有用户维度的 MT4 写路径必须经过统一 gate，不能只依赖连接总开关。
- 测试可使用本地 fake 验证 gateway、outbox 和状态机，但禁止真实 socket、HTTP 或外部 MT4 调用。
- scheduler 和 worker 在迁移期间不得消费开户、入金、出金或返佣 outbox。
- 最终数据中 `is_mt4_synced` 保持 0；本轮不把本地数据回写 MT4。

## 10. 初始密码策略

- 统一密码仅用于当前本地迁移和验收环境，明文为 `abc123`。
- `InitialDataSeeder`、`DatabaseSeeder`、`FrontDemoDataSeeder`、`LegacyFrontBusinessDataSeeder`、`DebugDataSeeder` 和相关迁移/命令使用同一配置来源，不再散落多套字符串。
- 前台代理、前台客户、后台管理员和大代理均使用 Laravel `Hash` 生成或使用经测试确认的 bcrypt hash。
- 正常用户注册仍使用用户提交的密码，不强制改成 `abc123`；“初始密码统一”只适用于安装、Seeder 和旧库迁移后的现有账号。
- 日志和报告不得输出 hash、旧密码或数据库凭据；只可输出经过人工批准的示例账号标识。

## 11. 中文注释验收

### 11.1 原则

- 文件级注释说明职责、输入、输出和明确不负责的内容。
- 方法级注释说明目的、参数来源、返回、异常或失败关闭语义；简单 getter 不机械添加无信息注释。
- 多阶段流程在阶段前解释目的；分支注释解释风险和业务语义，不复述 if/赋值/return。
- JWT、支付回调、MT4、上传、密码、权限、数据迁移等高风险链必须解释信任边界、脱敏要求和失败行为。
- 配置注释说明默认值、单位、安全含义和非法/缺失时行为。
- 注释必须与代码和测试一致，不保留过期迁移历史或虚构实现。
- HMAC 第 12 节固定口径只适用于项目实际存在的对应 HMAC 链；不为了满足文档凭空创建无需求的 HMAC 功能。

### 11.2 自动检查与人工复核

- 维护显式的一方源码注释清单和排除清单。
- 使用 `token_get_all()` 检查 PHP 文件级注释、具名方法邻接 PHPDoc、中文字符、参数和返回标签。
- 对抛异常的方法检查 `@throws` 或等价失败语义。
- 对 secret、Authorization、password、payload、Cache、MT4、支付回调和数据库迁移关键字命中的方法要求阶段注释和失败关闭说明。
- Blade、JS 和 CSS 只在存在非直观业务逻辑、兼容边界或复杂状态时补有意义的中文注释，不给每个标签和样式机械加注释。
- 机器检查只作为下界；高风险文件必须人工逐项核对注释是否解释“为什么”和“边界”，不能只统计数量。

## 12. Git 与交付规则

- 本轮禁止自动执行 `git add`、`git commit`、`git push`、强推或创建远端分支。
- Git 仅用于恢复远端历史、读取差异和生成待审核文件清单。
- `docs/` 全目录不得提交或推送到远端。
- 每个实施阶段结束后输出精确修改文件、测试证据和风险，由人工决定是否提交。
- 远端 fetch 失败不改变代码实施结果，但在声称“可推送”前必须重新验证远端连通性、认证和非快进冲突。
- 最终只能做推送预检；除非用户在看到待提交差异后再次明确授权，否则不执行提交和推送。

## 13. 最终交付证据

目标完成时必须提供以下当前状态证据，而不是引用旧报告：

1. 一方源码和注释范围清单及零未解释违规结果。
