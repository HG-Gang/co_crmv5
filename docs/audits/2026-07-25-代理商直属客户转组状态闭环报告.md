# 2026-07-25 代理商直属客户转组状态闭环报告

> 注释：本文件是“代理商直属客户转组”单一模块的阶段性审计记录，不代表旧项目全部 475 条路由方法已完成迁移。全量迁移进度仍以 `docs/audits/旧项目模块逻辑迁移核验矩阵.md` 为准。

## 1. 本次目标

将旧项目直属客户转组页面已展示、但旧写接口未二次校验的限制，下沉到新项目服务端。这样即使调用方不经过 Blade 页面、直接请求接口，也不能写入无效的转组申请。

本次覆盖的限制如下：

1. 代理只能为自己的直属普通客户申请转组，不能为间接客户或其它层级客户提交。
2. 新组不能等于客户当前组，避免产生没有业务意义的审核记录。
3. 客户已有任一条待审核转组申请时，不能再次申请。
4. 客户存在有效未平仓交易订单时，不能申请转组。

### 2.2 旧 Blade 的三道前端限制

旧页面 `resources/views/user/customer_list/customer_change_group.blade.php` 的逻辑为：

1. `isExistsOrder > 0` 时不显示提交按钮，页面提示“存在持仓，不能变更”。
2. `isExistsTrans = YES` 时不显示提交按钮，页面展示当前待审核申请。
3. JavaScript 在提交前比较旧组和所选组；两者相同时只提示“申请的变更账户类型不能与原账户类型一样”，不发起 HTTP 请求。

## 3. 项目二：新项目实现说明

新项目目录：`D:\Software\PhpProject\Demo\co_crmv5`。

### 3.1 路由映射

| 新路由 | 方法 | 输入 | 成功返回 | 失败返回 |
| --- | --- | --- | --- | --- |
| `POST /api/front/agents/group-change-applications` | `Front\AgentController::groupChange` | `target_user_id`、`new_group_id`、可选 `reason` | `code=1000`，`data` 为新 `trans_apply_logs` 记录 | 统一 HTTP 200，使用业务 `code` 表示失败原因。 |
| `POST /user/cust/change/group_edit` | `Front\AgentController::changeDirectCustGroupEdit` | 旧字段 `userId`、`grpName`、可选 `trans_apply_reason` | `msg=SUCCESS` | `msg=FAIL`；找不到启用组时为 `msg=CLASSINVALID`。 |

注释：旧兼容入口先把旧字段转换成现代字段，再调用 `groupChange()`；没有复制转组业务规则，避免两套校验逐渐偏离。

### 3.2 现代接口详细执行链路

1. `groupChange()` 用 Laravel Validator 验证 `target_user_id` 和 `new_group_id` 为必传整数，`reason` 最长 500 字符。
   - 校验失败：返回 `code=4005`，中文含义为“参数校验失败”。
2. `legacyFrontUserLogin()` 读取当前前台登录用户。
   - 未登录：沿用旧前台认证错误响应。
   - 非代理账号：返回 `code=4006`，中文含义为“权限不足”。
3. 方法进入 `DB::transaction()`，以 `lockForUpdate()` 锁定目标 `user_infos` 行。
   - 注释：同一客户的转组请求必须串行，避免两个并发请求同时看到“没有待审核申请”而各自插入一条记录。
4. 查询目标用户并验证 `account_type=2`。
   - 用户不存在：返回 `code=2008`，中文含义为“用户不存在”。
   - 目标不是普通客户：返回 `code=4006`。
5. 调用既有 `isDirectTransferTarget($agentId, $targetUserId)`。
   - 该方法通过 `FrontLegacyData::userScopeIds($agentId, false, null, true)` 同时兼容 `agent_descendants` 和 `user_infos.parent_id` 回退查询。
   - `directOnly=true` 只接受一层直属关系；间接客户返回 `code=4006`，不写入申请日志。
6. 查询并锁定目标组，要求 `is_enabled=1`；如果表存在 `category` 列，还必须为客户组 `category=2`。
   - 无效、禁用或代理组：返回 `code=4005`，中文含义为“组别无效”。
7. 比较 `targetInfo.group_id` 与 `new_group_id`。
   - 相同：返回 `code=2021`，中文含义为“操作不允许”；不写入申请日志。
8. 查询该客户未软删除的 `trans_apply_logs`，检查是否存在 `status=0`。
   - 存在待审核申请：返回 `code=2021`；不写入申请日志。
9. 查询 `user_trades`，使用 `UserTrade::open()` 的旧 MT4 哨兵值 `close_time='1970-01-01 00:00:00'`，并限制 `cmd in (0,1,2,3,4,5)`。
   - 存在有效持仓：返回 `code=2021`；不写入申请日志。
   - 注释：余额、信用等非持仓流水不在命令范围内，不能错误阻断转组。
10. 所有校验通过后，写入 `trans_apply_logs`。
    - `user_id`：目标客户。
    - `origin_group_id`：申请时的原组快照。
    - `group_id`、`group_name`：目标组快照。
    - `applicant_id`、`applicant_name`：当前代理快照。
    - `status=0`：中文含义为“待审核”。
    - `apply_reason`：申请原因；兼容旧表缺列时暂存到 `reject_reason`，避免迁移中丢失输入。
11. 事务提交并返回 `code=1000`，中文含义为“操作成功”。

### 3.4 新前端页面详细执行链路

1. `GET /user/cust/change/group/{uid}` 和 `GET /agent/group-change/{uid}` 都把路由中的数字 `uid` 注入共享 `module-page.blade.php` 的 `data-legacy-target-user-id`。
2. `module-page.js` 启动时先执行 `applyPendingFormValues()`，恢复客户列表快捷入口暂存的表单值；再执行 `applyLegacyTargetUserId()`。
   - 只有 `target_user_id` 为空、页面属于 `agent-group-change-module` 且 uid 为正整数时才回填。
   - 注释：快捷入口的值优先于路由默认值，避免用户已有的明确选择被覆盖。
3. 页面首次请求 `GET /api/front/agents/group-changes`，携带 `userId`、`groupId`、`startdate`、`enddate` 和分页参数。
4. 请求成功后保存 `res.data` 到 `currentMeta`，调用 `renderResponseDynamicOptions()`。
   - `available_groups` 是列表响应元数据，不再额外调用不存在的 `/api/front/available-groups` 路由。
   - 目标组下拉框使用“请选择”占位项；筛选型动态下拉仍使用“全部”占位项。
5. 共享表格渲染 `trans_uid`、`trans_type_gid`、`trans_apply_status`、`trans_apply_reason`、`rec_crt_date`。
6. 提交表单时调用 `POST /api/front/agents/group-change-applications`，成功后提示成功、重置表单并刷新列表；失败时保留表单内容并展示接口错误消息。

### 3.5 新前端页面与接口的结果闭环

| 页面结果 | 前端处理 | 后端结果 |
| --- | --- | --- |
| 客户 ID 已回填 | 用户无需重复输入，仍可手工修正空表单值 | 服务端重新验证代理、直属关系和客户类型。 |
| 组选项已加载 | 目标组下拉框有真实 `value/label` | 服务端重新验证组启用状态和 `category=2`。 |
| 申请成功 | 提示成功、清空表单、刷新申请列表 | 新增 `status=0` 的 `trans_apply_logs`。 |
| 同组/待审核/持仓被拒绝 | 提示接口错误，不清空输入 | 返回 `code=2021`，申请日志数量不增加。 |
| 跨树或间接客户被拒绝 | 提示权限不足，不清空输入 | 返回 `code=4006`，申请日志数量不增加。 |

### 3.3 旧兼容接口详细执行链路

1. `changeDirectCustGroupEdit()` 根据 `grpName` 查询启用的 `group_configs`。
   - 查询失败：返回 `msg=CLASSINVALID`，中文含义为“组别无效”。
2. 把 `userId` 映射为 `target_user_id`，把已解析组 ID 映射为 `new_group_id`，把 `trans_apply_reason` 映射为 `reason`。
3. 调用现代 `groupChange()`，因此依次执行直属客户、同组、待审核、持仓和并发锁定判断。
4. 现代响应 `code=1000` 时返回 `msg=SUCCESS`；任一业务失败时返回 `msg=FAIL`。
