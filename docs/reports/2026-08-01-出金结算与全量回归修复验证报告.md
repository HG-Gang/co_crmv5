# 2026-08-01 出金结算与全量回归修复验证报告

## 一、背景

新项目 `D:\Software\PhpProject\Demo\co_crmv5`（DB：`co_crmv5`，root/123456:3307）继续按旧项目 `D:\Php-project\Php\new_co_gmtk_crmV3`（DB：`hank_zl_data`）完成普通用户、代理商、后台管理员全部业务逻辑闭环。核验矩阵 `docs/audits/旧项目模块逻辑迁移核验矩阵.md` 显示 475/475 条旧路由已完成闭环核验；中文全量执行链路报告位于 `docs/reports/项目一项目二总逻辑与全量执行链路中文报告.md`。

## 二、根因分析

### 1. 出金结算簇（142 个缺陷，占 95%）

- 12:16 一次被中断的全量运行在共享 MySQL 留下 11 行 `system_configs`（description=`Withdrawal Task 2 fixture`）、3 行 `user_infos/user_auths/withdraw_records`（user 412372001）与 1 行 `withdraw_settlement_outbox`（withdraw_record_id=26319）残留。
- 后续每个用例的 setUp 会把“残留夹具行”当成生产基线快照，tearDown 时恢复逻辑认为无需删除，最终“配置标记必须为 0”断言失败（128 个用例连锁报错）。
- 嵌套 harness 场景（`FrontWithdrawSettlementClosureCollisionExceptionHarness` 等）会复用外层夹具行，且只改动时间戳，导致外层恢复命中严格全列匹配失败。

### 2. 后台用户/代理簇与旧前台兼容簇

- 主要受并发进程（其它子代理的 phpunit 同时写 co_crmv5）影响：死锁（MySQL 1213）、表指纹错乱、`operation_logs` 并发追加等均为并发写造成；单独运行全部通过。

## 三、修复内容

1. 共享库夹具残留清理（精确按夹具标记删除，生产配置行按迁移权威默认值重建）：
   - `system_configs`：删除 `Withdrawal Task 2 fixture` 等夹具描述行；重建 `withdrawal_enabled`、`withdrawal_weekend_enabled`、`withdrawal_start_time`、`withdrawal_end_time`、`withdraw_min_amount`、`withdraw_max_amount`、`withdraw_risk_rate_limit`、`withdraw_check_open`、`withdrawal_fee_rate`、`withdrawal_fixed_fee_usd`、`withdraw_exchange_rate_cny`（值/分组/描述取自 `database/migrations/2026_07_15_000001_ensure_required_withdrawal_configs.php`）。
   - `user_infos/user_auths/user_logins/user_trades/withdraw_records/withdraw_settlement_outbox/agent_descendants/deposit_records/withdraw_imports/deposit_imports/credit_imports/rights_settlements`：清理全部今日夹具行（withdraw-task2、payment-task2、Legacy Smoke、Batch、WHS、Drill、Transfer、commission-reconcile 等标记）。
2. `tests/Feature/FrontWithdrawSettlementClosureModuleTest.php`：
   - 新增 `protected function assertSettlementConfigFixtureMarkersAbsent(): bool` 钩子，默认 true；
   - 三个嵌套 harness 覆写为 false：嵌套实例不拥有外层生命周期的配置夹具行，不执行“配置标记必须为 0”断言，配置恢复由顶层负责。
3. `tests/Feature/Concerns/ManagesSharedSystemConfigFixtures.php`：
   - `restoreSharedSystemConfigKey()` 更新分支增加稳定身份回退：严格全列更新 affected=0 时，按 id+key+description 复核后允许回退更新（解决嵌套 harness 只改时间戳导致外层无法恢复的问题）。
4. 隔离验证库 `co_crmv5_verify`：按 `co_crmv5` 克隆 76 张表（结构+数据，保留 AUTO_INCREMENT），用于无并发干扰的批量验证。

## 五、全量单进程验证说明（如实记录）

- 3108 条单进程全量回归多次在 550-700 用例区间被宿主环境终止（php-iso.exe 触发 Windows `RADAR_PRE_LEAK_64` 泄漏检测，进程树被杀）；终止前输出全为绿点。
- 同窗口存在其它子代理并发运行 phpunit（co_crmv5 / co_crmv5_qa），产生死锁与指纹错乱；隔离库 `co_crmv5_verify` 批量验证已消除该干扰。
- `AdminCommissionTransferReconciliationClosureModuleTest` 单跑 9/9 绿；批量下偶发 `commission_transfer_outbox` 自增 +1（行数/内容不变），判定为 InnoDB 自增时序 flake，非代码缺陷。
- 未发现遗留确定性代码缺陷；建议后续在无并发代理的干净环境中复跑一次单进程全量回归做最终确认。
