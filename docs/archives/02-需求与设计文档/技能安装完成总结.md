## 📦 Karpathy Guidelines（1个）

### karpathy-guidelines
**作用：** Andrej Karpathy 的编码代理行为准则

**四大核心原则：**
1. **只实现被要求的功能** - 不添加未请求的抽象、配置性或"灵活性"
2. **进行精准的外科手术式修改** - 保持修改最小化、聚焦、成比例
3. **提前说明假设** - 明确陈述假设而不是静默推进
4. **定义可验证的成功标准** - 在实现前指定如何验证

**何时使用：** 所有编码任务的基础纪律，防止过度工程和功能蔓延

## 🚀 Superpowers 核心技能（14个）

### 1. using-superpowers（入口技能）⭐
**作用：** 建立如何查找和使用技能的规则
**何时使用：** 开始任何对话时 - 如果有 1% 可能性某个技能适用，必须调用它
**关键规则：** 在任何响应或操作之前调用相关技能

### 2. brainstorming
**作用：** 将创意转化为完整设计的头脑风暴流程
**何时使用：** 任何创造性工作之前 - 创建功能、构建组件、添加功能或修改行为
**核心流程：** 探索项目上下文 → 提问澄清 → 提出 2-3 种方法 → 呈现设计 → 编写设计文档 → 转向实施

### 3. writing-plans
**作用：** 编写详细的实施计划
**何时使用：** 当你有规格说明或多步骤任务需求时，在接触代码之前
**关键特点：** 假设工程师零上下文，每个步骤 2-5 分钟，包含完整代码，无占位符

### 4. subagent-driven-development（推荐）⭐
**作用：** 通过派遣新子代理执行每个任务，两阶段审查（规格合规 → 代码质量）
**何时使用：** 执行具有独立任务的实施计划，当前会话中
**核心优势：** 新鲜上下文、自然遵循 TDD、两阶段审查、快速迭代

### 5. executing-plans
**作用：** 在单独会话中执行实施计划，带审查检查点
**何时使用：** 当没有子代理可用时，或需要在并行会话中执行
**关键：** 如果有子代理支持，优先使用 subagent-driven-development

### 6. test-driven-development（TDD）⭐
**作用：** 强制 RED-GREEN-REFACTOR 循环
**何时使用：** 实施任何功能或错误修复时，在编写实现代码之前
**铁律：** 先写测试、看它失败、编写最小代码使其通过，没有例外
**关键原则：** 如果你没有看到测试失败，你不知道它测试的是否正确

### 7. systematic-debugging
**作用：** 4 阶段根因调试流程
**何时使用：** 遇到任何 bug、测试失败或意外行为时，在提出修复之前
**4 个阶段：** 
1. 根因调查（收集证据）
2. 模式分析（查找工作示例）
3. 假设和测试（一次一个变量）
4. 实施（创建失败测试 → 修复 → 验证）
**铁律：** 没有根因调查就不能修复

### 8. verification-before-completion
**作用：** 完成前的验证门控
**何时使用：** 即将声明工作完成、修复或通过时，在提交或创建 PR 之前
**铁律：** 没有新鲜验证证据就不能声称完成
**5 步门控：** 识别命令 → 运行 → 读取输出 → 验证 → 然后声称

### 9. finishing-a-development-branch
**作用：** 完成开发分支的结构化选项
**何时使用：** 实现完成，所有测试通过，需要决定如何集成工作
**流程：** 验证测试 → 检测环境 → 呈现选项 → 执行选择 → 清理

### 10. using-git-worktrees
**作用：** 确保工作在隔离的工作空间中进行
**何时使用：** 开始需要与当前工作空间隔离的功能工作，或执行实施计划之前
**核心原则：** 先检测现有隔离 → 然后使用原生工具 → 然后退回到 git

### 11. requesting-code-review
**作用：** 派遣代码审查子代理
**何时使用：** 完成任务、实施主要功能或合并前验证工作
**强制性：** 每个任务后（subagent-driven development）、完成主要功能后、合并到主分支前

### 12. receiving-code-review
**作用：** 技术性评估代码审查反馈
**何时使用：** 接收代码审查反馈时，在实施建议之前
**核心原则：** 实施前验证，假设前询问，技术正确性优于社交舒适度
**禁止响应：** "你完全正确！"、"好点子！"、感谢表达

### 13. writing-skills
**作用：** 创建新技能的 TDD 方法
**何时使用：** 创建新技能、编辑现有技能或在部署前验证技能
**铁律：** 先写失败测试再写技能（与代码 TDD 相同）
**流程：** RED（基线行为）→ GREEN（编写技能）→ REFACTOR（堵住漏洞）

### 14. dispatching-parallel-agents
**作用：** 并行派遣代理处理独立任务
**何时使用：** 面对 2+ 个可以在没有共享状态或顺序依赖的情况下工作的独立任务
**关键优势：** 并行化、聚焦、独立性、速度（3 个问题在 1 个的时间内解决）

## 🎯 技能体系总结

### 工作流程链

**完整开发流程：**
```
using-superpowers（检查技能）
    ↓
brainstorming（设计）
    ↓
writing-plans（计划）
    ↓
using-git-worktrees（隔离工作空间）
    ↓
subagent-driven-development（执行，每个任务后审查）
    或
executing-plans（批量执行）
    ↓
test-driven-development（TDD 贯穿实施）
    ↓
systematic-debugging（遇到问题时）
    ↓
verification-before-completion（完成前验证）
    ↓
finishing-a-development-branch（完成）
```

### 协作流程
```
requesting-code-review（请求审查）
    ↓
receiving-code-review（接收反馈）
```

### 并行工作
```
dispatching-parallel-agents（独立任务并行）
```

### 元技能
```
writing-skills（创建新技能）
```

## 🔥 核心哲学对比

### Karpathy Guidelines
- **焦点：** "不做什么"
- **防止：** 过度工程、功能蔓延、静默假设
- **强调：** 验证循环、外科手术式修改
- **适用：** 所有编码任务

### Superpowers
- **焦点：** 完整的开发方法论
- **提供：** 测试驱动开发、系统化调试、子代理驱动流程
- **强调：** 流程纪律、验证门控、质量保证
- **适用：** 整个软件开发生命周期
