## 二、两份差距报告均为解析偏差，不是真实缺口

1. `_gap_report.txt`（11:42）使用正则只匹配 `'Controller@method'` 字符串形式路由；
   新项目大量路由使用 `'Front\AuthController@register'` 形式且带 `user/` 等前缀，
   导致报告误判为“旧路由目标缺失”。
2. `_uri_gap_report.txt`（11:43）按“原始 URI + Controller@method”完全相等比对；
   旧路由使用分组前缀（如 `center` 实际是 `user/center`），新项目按 `user/center/...`
   展开，因此全部被标记为未覆盖。
3. 真实证据：新项目 `route_list.json` 共 800 条路由，旧项目 392 个唯一目标；
   `FrontLegacyRouteCompatibilityTest` 等测试文件对 legacy 路由契约做了强制断言。

## 三、全量测试套件 E/F 根因：共享开发库并发写演示用户

### 现象

- 全量套件（3108 个用例）运行中段被中断；已跑部分出现约 30 个 E 和少量 F。
- 单独重跑 `tests\Feature\FrontLegacyRouteCompatibilityTest.php` 三次，
  失败数分别为 3 / 2 / 3，失败用例：
  - `front legacy public smoke routes do not crash`（200 ↔ 302 断言失败）
  - `front legacy page routes render without crashing`（302 ↔ 200 断言失败）
  - `front legacy profile ajax routes resolve real legacy session user`（死锁）

### 根因

1. 测试基座使用 `DatabaseTransactions`，直接操作共享开发库 `co_crmv5`
   （phpunit.xml 中 sqlite 配置被注释，未使用独立测试库）。
2. 测试内 `ensureDemoRootAgent()` 对 `user_infos.user_id=1001`（登录
   `agent@test.com`）执行 `updateOrInsert`；该行同时被运行中的 Web 服务
   （`php artisan serve`，供前端合规子智能体浏览器测试使用）和
   `agent_db_migration_audit` 并发读写。
3. 同一行上的两笔写事务形成锁等待，InnoDB 判定死锁，回滚一方并返回
   `SQLSTATE[40001] 1213`。死锁回滚后演示用户状态不完整，连带
   `front legacy page routes` 等页面路由的 302/200 断言失败。

### 证据

```
SQLSTATE[40001]: Serialization failure: 1213 Deadlock found when trying to get lock
update `user_infos` set ... where (`user_id` = 1001) limit 1
```

失败随重跑变化（3/2/3），符合“外部并发写、间歇性触发”特征，而非确定性代码缺陷。

### 修复建议（按优先级，需协调者决策后执行）

1. 全量测试期间暂停对共享库的写操作：停掉 `php artisan serve` 或让浏览器
   子智能体暂停交互，测试跑完再恢复（改动最小，立即可行）。
2. 建立独立测试库 `co_crmv5_test`（phpunit.xml 打开独立连接配置，测试前
   `migrate:fresh --seed`），彻底隔离测试与开发数据（结构性根治，推荐）。
3. 若短期内无法隔离，将测试演示用户从固定 `user_id=1001` 改为每次测试
   独立生成的用户 ID，并同步修改依赖该用户的 legacy 会话用例（改动面较大，
   涉及多个 Feature 文件，需评估）。
