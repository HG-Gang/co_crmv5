# 2026-07-25 旧前台实时返佣汇总闭环报告

> 本文只记录旧路由 `GET /user/position/comm_summary` 的迁移闭环，不代表旧项目全部模块已经完成。全量迁移进度以 `docs/audits/旧项目模块逻辑迁移核验矩阵.md` 为准。

## 1. 本轮目标与原问题

旧项目的 `comm_summary` 是由定时器免登录触发的实时返佣入口，并不是持仓页面。项目 2 原先把同一路径映射到 `LegacyPageController@positionSummary`，因此只会渲染 Blade，旧返佣筛选、代理链计算、MT4 入金和已处理标记都没有执行。

本轮把该入口重写为可审计的返佣批处理，并补齐三项资金安全边界：并发幂等、外部调用结果状态区分、以及多级返佣全部完成后才结束源交易。

## 2. 项目 1：旧项目执行链路

旧项目目录：`D:\Php-project\Php\new_co_gmtk_crmV3`

1. 路由 `GET user/position/comm_summary` 指向 `User\\PositionSummaryController@_exte_mt4_sync_comm_summary`，并在 `LoginMiddleware` 的例外列表中，因此它是定时任务入口。
2. 控制器在 `trades_start` 开关允许执行时，从 `mt4_trades` 查询 `CMD in (0..5)`、已平仓、成交量非零、手续费非零、且不在 `user_trades.voided=1` 的最多 30 笔交易。
3. 控制器沿客户 `parent_id` 递归查询 `agents`，每一层计算 `当前代理 comm_prop - 下级 comm_prop`，读取当前代理组的 `user_grup_radix`，按 `volume / 100 * 差额 / 100 * radix` 计算返佣金额。
4. 当 `settlement_model=1` 且金额大于零时，以 `DBCN{交易用户ID}-#{交易单号}` 备注调用 MT4 入金；无需线上结算时只写已处理记录。
5. 旧代码依赖 MT4 评论字段去重，并在一条返佣腿成功后写 `user_trades.voided=1`。该策略不能表达多级腿的完整状态，也无法可靠处理外部调用异常。

旧方法没有稳定 JSON 返回体，调用方只能从日志了解处理结果。

## 3. 项目 2：新执行链路

### 3.1 路由和返回

1. [`routes/web.php`](D:/Software/PhpProject/Demo/co_crmv5/routes/web.php:366) 保持旧 URL 与 `GET` 方法，改到 `LegacyCommissionSummaryController@commSummary`，避免定时任务被误导到持仓页面。
2. [`LegacyCommissionSummaryController.php`](D:/Software/PhpProject/Demo/co_crmv5/app/Http/Controllers/Front/LegacyCommissionSummaryController.php:30) 调用服务并返回标准 JSON。`code=1000` 表示请求已执行；`data` 中的统计值如实反映成功、可重试和失败，不伪造成功结果。
3. [`LegacyCommissionSummaryService.php`](D:/Software/PhpProject/Demo/co_crmv5/app/Services/Legacy/LegacyCommissionSummaryService.php:66) 仍限制每批 30 条，用 `user_trades.settlement_status=0` 表达尚未闭环的源交易。

### 3.2 每笔交易的闭环

1. 服务先验证客户、客户组与上级链。客户组不返佣或没有上级时，源交易直接标记完成，表示“无需线上返佣”。缺少资料、账号类型错误或出现环状代理链时，源交易保持未结算并计为失败。
2. 从直属上级逐级向上计算返佣：`user_infos.comm_rate` 对应旧 `comm_prop`，`group_configs.radix` 对应旧 `user_grup_radix`。公式为 `volume / 100 * (上级比例 - 下级比例) / 100 * 收款代理组基数`。
3. 每个“源交易 + 收款代理”先写入 [`commission_rebate_payouts`](D:/Software/PhpProject/Demo/co_crmv5/database/migrations/2026_07_25_000001_create_commission_rebate_payouts_table.php:42)，唯一索引和行锁保证并发触发时同一代理不会重复收到 MT4 入金。
4. 服务在事务中把可执行腿声明为 `processing`，在事务外调用 MT4。外部成功且取得数字票据号时，在同一事务写入 `commission_records` 和 `settled` 状态。
5. MT4 明确未收到命令时写 `retryable`，表示可以在 `available_at` 后自动重试；明确拒绝时写 `rejected`，表示未入账且等待业务处理。
6. MT4 返回未知、调用异常或外部成功后的本地提交失败时写 `unknown`，表示可能已入账，禁止自动重发，必须人工核对。本轮补足了网关抛异常时立即进入该状态的逻辑。
7. 只有所有返佣腿都是 `settled` 或 `not_payable` 时，才写 `user_trades.settlement_status=1`。任一 `retryable`、`rejected`、`unknown` 或处理中的腿都会阻止源交易完成。

### 3.3 JSON 统计字段

| 字段 | 中文含义 | 结果说明 |
| --- | --- | --- |
| `scanned_count` | 扫描的源交易数 | 本批最多 30 条候选交易。 |
| `settled_count` | 已确认入账的返佣腿数 | 每名上级代理成功一笔，计数加一。 |
| `retryable_count` | 可安全重试的返佣腿数 | MT4 明确未接收，源交易仍未完成。 |
| `failed_count` | 拒绝、未知或资料异常数量 | 需要人工核查，源交易仍未完成。 |
| `skipped_count` | 无需线上结算的数量 | 线下结算、非正差额或非返佣组。 |
| `completed_trade_count` | 已闭环的源交易数 | 所有返佣腿均已结束后增加。 |
